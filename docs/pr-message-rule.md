# PR 메시지 규칙

> 적용 대상: 이 저장소의 모든 PR (사람이 쓰든 AI 에이전트가 쓰든 동일)
> 관련 규칙: [AGENTS.md](../AGENTS.md)의 브랜치 규칙 (beta에서 분기, beta로 PR)
> 본문 골격은 [.github/pull_request_template.md](../.github/pull_request_template.md)가 자동으로 채워줘요.

PR은 리뷰 단위예요. 제목은 무엇을 바꿨는지 한 줄로 압축하고, 본문은 리뷰어가 코드를 읽기 전에 맥락·근거·검증 상태를 잡을 수 있게 써요.

## 제목

- 형식: `<type>: <요약>`
  - `type`: `feat` / `fix` / `refactor` / `docs` / `chore` / `perf` (커밋 컨벤션과 동일)
  - 요약은 변경의 핵심을 명사·현재형으로 한 줄에.
  - 범위가 넓어 부제가 필요하면 쉼표·콜론·괄호로 이어 붙여요. em dash(U+2014)나 en dash(U+2013)는 쓰지 않아요.
- 예시:
  - `feat: 웰컴 카드 축소(800×450)와 인사 카드 편집기 UX 개편`
  - `fix: 대시보드 빌드 실패 수정 (클라이언트 번들로 새어 들어간 pg 제거)`
  - `refactor: 길드 데이터 request/reply 경로 정리`

## 본문

유형에 따라 구조를 달리해요. 공통 필수 섹션은 검증이에요. 해당 없는 섹션은 지워요.

### feat / refactor (기능·구조 변경)

- `## 요약`: 무엇이 어떻게 바뀌었나. 영역이 여럿이면 표나 불릿으로 나눠요.
  - 기존 동작과의 호환성(데이터 마이그레이션 필요 여부, 저장 형식 변경, 비호환 API)을 반드시 명시해요.
- `## 결정 로그`: 되돌릴 수 있는 설계 선택과 그 이유를 한 줄씩. 명시적으로 안 한 것(비목표)도 남겨요. 설계 판단이 필요할 때만 작성해요.
- `## 검증`

### fix (버그 수정)

- `## 배경`: 어떻게 발견됐나. 재현 절차, 에러 메시지, 로그, 이슈 링크 등 증거를 남겨요.
- `## 원인과 수정`: 왜 발생했나, 무엇을 바꿨나. 단순하면 한 문단으로 합쳐도 돼요.
- `## 검증`

## 검증 규칙 (필수)

- 실제로 실행한 커맨드와 결과를 써요. (예: `yarn lint`, `yarn typecheck`, `yarn test`, `yarn turbo build --filter=@sirubot/dashboard`)
- 확인하지 못한 것은 "미검증"으로 명시해요. 추측을 확인한 것처럼 쓰지 않아요.
- 수동 확인이 필요한 항목(UI 육안 확인, 런타임 동작, 배포 후 확인)은 체크리스트로 남기고, `[x]`는 실제로 확인한 것만 표시해요.
- 버그 수정이면 수정 전 재현과 수정 후 결과의 대조를 남겨요.
- CI가 이 브랜치에서 도는지, 머지 후 확인되는지도 검증에 포함해요.

## 공통 규칙

- 본문은 한국어로 작성해요. 코드 식별자·경로·커맨드·에러 메시지는 원문을 유지해요.
- 과장된 형용사나 검증되지 않은 수치 없이 사실만 써요.
- UI가 바뀌면 스크린샷이나 GIF를 본문에 포함하고, 리뷰어가 확인할 지점을 명시해요.
- 커밋이 여러 개면 영역별로 정리해 커밋 쪼개기와 본문이 대응되게 해요.
- 관련 이슈·문서·PR은 링크로 연결해요.
