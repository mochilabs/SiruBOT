# Bot Ops (audio, state, sharding)

Audio runs on `lavalink-client` v2 with external Lavalink servers. NEVER suggest `@discordjs/voice`, yt-dlp, or play-dl — none exist here.
Triage by layer first: voice/playback pipeline ↔ Redis/DB state ↔ sharding.

## Audio pipeline
1. `setupAudio(nodes, shardInfo)` (`core/botApplication.ts`, called from `setupLavalink` in `core/lavalinkSetup.ts` before Lavalink handler registration) options: retryAmount/retryDelay, autoSkip, onEmptyQueue destroyAfterMs + `autoPlayRelated`, maxErrorsPerTime, sendToShard.
2. Handlers in `features/music/lavalink/handlers/` (6 files): `trackHandler` (trackStart/trackEnd/trackStuck/trackError/queueEnd/playerDestroy; stops after `consecutiveErrors >= MAX_CONSECUTIVE_ERRORS`, env-overridable); `nodeHandler` (on connect: updateSession + store session; on disconnect: redistributes orphan players round-robin to `leastUsedNodes('playingPlayers')` — zero-node guard exists, do NOT change this logic out of error concerns); `playerHandler`, `base.ts`, `lavalinkHandler` (`cleanup()` at shutdown). Handlers take `LavalinkDeps` (`features/music/lavalink/deps.ts`, the `container.lavalink` object built in `BotApplication.setupServices`) and never read `container`; `architecture.test.ts` guards that with `LAVALINK_CONTAINER_ALLOWED` (empty).
3. Adding tracks: `container.musicPlay` (`features/music/application/play.ts`, `createMusicPlay`) decides the voice channel (`canAddTracks`), then calls `AudioService` (`features/music/application/audioService.ts`): getOrCreatePlayer → search (loadType error/empty) → connectPlayer (permissions) → enqueueTrack → ensurePlayback. Entry points (`/재생`, `/검색`, command channel, AI `music_play`, web player) render their own replies from the result (`features/music/discord/utils/playFeedback.ts`). Narrow failures to a step.
4. Voice connection issues: `features/music/discord/listeners/raw.ts` (voice payload → Lavalink), `voiceStateUpdate.ts` (5-minute empty-channel leave, deaf filter).

## Playback control policy
Pause/resume/volume/repeat/seek/stop/skip-now/previous go through `container.music` (`features/music/application/{actor,access,control}.ts`); slash subcommands, controller buttons, the dashboard web player responder (`features/music/inbound/playerWeb.ts`) and AI tools are adapters. One policy in `access.ts`: same voice channel as the bot plus "DJ role or alone"; Administrator, ManageGuild and DJ-role holders (`hasRemoteControl`) are exempt from both and may control from outside voice. Adding tracks follows `canAddTracks` (same voice channel for anyone; remote controllers from anywhere while the bot is in a channel), and the dashboard's `canPlay`/`canControl` flags are computed with the same functions. Violations throw `AppError('forbidden')`. Slash vote-skip is `createVoteSkip` (`features/music/application/voteSkip.ts`, `container.voteSkip`): it decides immediate skips or opens a vote, and performs the skip through `container.music.skipApproved` (no second access check, so the vote policy is not replaced by DJ-or-alone). Discord only renders the vote (`features/music/discord/managers/voteSkip.ts`).

## State persistence (Redis queues/sessions | Prisma)
5. Queue: `CachedQueueStore` in `queue/queueStore.ts` — Redis first → MemoryCache (TTL 30 min, max 1000) → empty queue. On Redis disconnect, pendingWrites accumulate and sync onConnect. Redis key TTL 7 days (`REDIS_TTL_SECONDS`), key `lavalink/queue/<guildId>`. For loss reports, narrow to pendingWrites miss / TTL expiry / key mismatch.
6. Session resume: `NodeSessionStore` in `redisStore.ts` (sessionId per shard key). Restore logic lives in `features/music/lavalink/handlers/sessionRestore.ts` (`nodeHandler` delegates). `handleResumedPlayers`: filters unconnected and 5-min-stale players (`RESUME_STALE_THRESHOLD_MS`), then batch (`RESTORE_BATCH_SIZE` 10) parallel restore; guilds whose cache hasn't arrived go to `pendingGuildPlayers`, polled for 90 s (`GUILD_WAIT_TIMEOUT_MS`) then restored/cleaned. Restore order: savedPlayer lookup → createPlayer → controller fetch → queue sync → assign current/position. Fresh-session ops on `resumed===false`: `restoreFreshSession/restoreFreshGuild/restoreFreshPlayer` with 6 h freshness (`FRESH_RESTORE_MAX_AGE_MS`) and empty-voice-channel occupancy check.
7. PlayerSaver: set on playerCreate/Update, delete on playerDestroy — check delete-before-save races. Prisma (`packages/prisma/src/schema.prisma`): `PlaylistTrack @@unique([playlistId, position])` reorder races, `GuildTrackHistory` index, onDelete propagation. `trackStart`'s increasePlays→addHistory is fire-and-forget (logger.error only) — candidate cause for missing stats.

## Sharding
8. Boot branch (`core/bootstrap.ts` → `core/shardIdentity.ts`): `NODE_ENV !== 'production'` → standalone shard `[0]`. Production requires `SHARD_MANAGER_URL`; on `NoShardsAvailableError`, infinite retry with `SHARD_IDENTIFY_RETRY_MS` (min 1000 ms) — slot contention during rolling updates is normal, do not "fix" with exit logic.
9. Status: `reportStatus('ready')` + `onStats` (guild count, player count, heap, uptime). For dashboard/shardmanager count mismatches, check this callback first. 5 shard listeners (`apps/bot/src/discord/listeners/shard/`): disconnect, Error, Ready, Reconnecting, Resume.
10. Health (`core/healthServer.ts`): `HEALTH_PORT` (default 8080) HTTP 200/503 based on `client.isReady()` — 503 only before READY; temporary reconnects after READY get 200 for a 120 s grace. `wsStatus` is included in body but not used for the verdict. A 503 may be a Discord WS issue, not Lavalink — separate causes.

## Shutdown order (`core/shutdown.ts`, wired in `core/bootstrap.ts`) — violations lose sessions; flag in review
healthServer close → Lavalink node session Redis save → `lavalinkHandler.cleanup()` + `audio.removeAllListeners()` → stop the shared Redis subscription in `container.redisSubscribers` (one connection carrying every responder and event listener; the bindings list is assembled in `BotApplication.setupServices`, `core/botApplication.ts`, and a new responder is added there only) → run every `stop()` in `container.stoppables` (state owners such as AI chat history, counting state, playback reporter, ticket channel deletes, timer owners; parallel, failures logged, bounded by `STOPPABLES_TIMEOUT_MS`; contract in `lib/lifecycle.ts`) → pendingWrites journal flush → redis disconnect → db disconnect → `client.destroy()` → `shardClient.destroy()` → `Sentry.close(2000)`.

A new owner of debounced/buffered writes or timers must implement `Stoppable` and be pushed to `container.stoppables` when created, so its `stop()` runs before Redis and the DB close.

Answer style: no guessing. Pinpoint the failing step from logs/events/config; give confirmation logs and repro conditions (dev/prod, shard count, node count) per hypothesis. Minimal-diff fixes. Trace data flow (write → read → restore); state race/TTL assumptions explicitly. Schema changes: mention `yarn workspace @sirubot/prisma migrate:dev`.
