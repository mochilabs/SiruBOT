# SiruBOT Agent Instructions

Discord music bot monorepo (Turborepo + Yarn 4, Node 22+, ESM). Apps: `bot` (Sapphire + lavalink-client), `dashboard` (Next.js, :3000), `shardmanager` (:3001), `data-api` (gateway, Redis hub, LLM jobs, :3002), `storage` (public asset URLs, :3003), `notifier` (stream alerts → webhooks, :3004). Packages: `prisma`, `utils`, `app-kit` (shared Fastify auth/env/logger), `shardclient`, `isrc` (ISRC lookup for the track chart), `cards` (Takumi card nodes shared by data-api and the dashboard).

- Per-package rules: read the package's `AGENTS.md` before working in it (index below). This file holds only what applies across packages.
- Docs under `docs/` are English; cite file paths, never line numbers. `docs/` holds only documents linked from the root `README.md`; working notes (plans, audits, changelogs) go in `Localdocs/` (gitignored). References: `docs/architecture.md`, `docs/api-{dashboard,data-api}.md`, `docs/setup-dev.md`, `docs/runbook-production.md`.
- Skills: read `.claude/skills/<id>/SKILL.md` before working in its area; don't copy a skill's rules elsewhere. Bot: `sapphire-command`, `component-view`, `discord-components-v2`, `bot-features` (AI chat, TTS, mixer, lyrics, temp voice, games), `bot-ops` (playback, Lavalink, sessions, shards, shutdown). Dashboard: `dashboard-conventions`, `dashboard-ui`. General: `repo-infra`, `security-audit`.

## Package index

Each has an `AGENTS.md` (rules) and a `CLAUDE.md` that only imports it.

Each app's file ends with a **Run and test** section (start, port, health check, what else must be running, a single-test example).

- `apps/bot`: feature layout, service `deps` injection, custom IDs, lifecycle, architecture guards.
- `apps/dashboard`: Next.js version notice (generated by `next dev`), skills, utils subpath imports.
- `apps/data-api`: Redis hubs, providers/renderers, env and key chains, LLM endpoints, schedulers.
- `apps/notifier`: stream sources, webhook-token encryption and `AUTH_KEY` rotation, push opt-in env.
- `apps/storage`: object routes, `STORAGE_PUBLIC_URL` and data volume.
- `apps/shardmanager`: shard assignment, allocation grace, HTTP key.
- `packages/shardclient`: the shardmanager WS protocol schemas.
- `packages/utils`: cross-app contracts, subpath exports, Redis channel contracts.
- `packages/app-kit`: shared Fastify auth, env, error handler, logger.
- `packages/isrc`: provider contract, matching rule, MusicBrainz User-Agent.
- `packages/cards`: runtime-independent Takumi card pieces (tokens, artwork helpers, `greetingCard`); no node-only imports in the root export.
- `packages/prisma`: schema, migrations, client generation. More conventions in the `repo-infra` skill.

## Service map

| App | Port | Health (no auth) | Needs to run locally |
|---|---|---|---|
| bot | health only, `HEALTH_PORT` 8080 | `GET /` | PostgreSQL, Redis, a Lavalink node. data-api for gateway features (weather, lyrics, cards). Dev mode needs no shardmanager |
| dashboard | 3000 | none | PostgreSQL, Discord OAuth app. data-api + a running bot for channel/role/player features |
| shardmanager | 3001 | `GET /api/health` | `DISCORD_TOKEN` and `AUTH_KEY`. Production bots require it; dev bots skip it |
| data-api | 3002 | `GET /api/health` | Its auth key. Redis for hubs, PostgreSQL for memory tidy, ISRC and Wrapped |
| storage | 3003 | `GET /health` | Its auth key and `STORAGE_PUBLIC_URL`. No DB |
| notifier | 3004 | `GET /health` | Its auth key and PostgreSQL. Redis plus a running bot to create webhooks |

Backend apps run from `dist/`: build first (`yarn workspace @sirubot/<app> build`, or keep `yarn watch` running), then `yarn workspace @sirubot/<app> start`. `docker/docker-compose.yml` starts Redis, PostgreSQL and a plugin-less Lavalink (no YouTube or mixer; `docs/setup-dev.md`).

## Branches and PRs

- Branch from `beta`. Never commit directly to `beta` or `main`. PR base is **always `beta`** (`main` is the deploy snapshot; fix with `gh pr edit <N> --base beta`).
- Titles and bodies follow `docs/pr-message-rule.md`: list verification run and what is unverified; UI changes include screenshots.

## Commands

- `yarn generate` (Prisma client) is required before typecheck/build. `yarn dev` runs only the dashboard; `yarn watch` builds everything else. Dashboard `dev` uses `--webpack`, `build` uses `--turbopack`.
- Single test: `yarn workspace @sirubot/bot test src/path/file.test.ts`. If it prints `command not found: vitest`, use `yarn turbo test --filter=@sirubot/bot -- src/path/file.test.ts`.
- Tests use the root `vitest.config.ts`, which aliases `@sirubot/utils` and `@sirubot/app-kit` to **source** (no dist build needed). The dashboard has its own `apps/dashboard/vitest.config.ts`.
- Never run bare `tsc`; `yarn typecheck` builds dependencies first.
- Lint is prettier `--check` everywhere except the dashboard (`eslint --max-warnings=0`). The pre-push hook runs `lint:fix` + typecheck.

## Cross-app communication

Apps never import each other. Contact points: Redis pub/sub, HTTP with a shared key, the shardmanager WS protocol.

- **Redis channel names and schemas live only in `packages/utils/src/redisChannels.ts`**, bundled as contracts in `redisContract.ts` (`defineRedisRpc`, `defineRedisEvent`, `defineRedisGuildEvent`). Never hardcode channel strings; wire strings must stay byte-identical across a rolling deploy (`redisContract.test.ts` pins them).
- **The dashboard never talks to the bot directly.** Bot-bound work goes dashboard API route → data-api (HTTP) → Redis → bot.
- Work needing the bot token or gateway cache uses **request/reply**: publisher sends `*:request` with a `requestId`, only the bot owning the guild replies on `*:response`. Copy an existing pair (data-api hubs built with `createRequestReplyHub`; bot side `createRedisResponder`, handlers in `features/*/inbound/`).
- Live player: bot → `sirubot:player:{guildId}` → data-api `playerHub` → SSE → dashboard. Settings saves broadcast `sirubot:guild-settings:invalidate`.
- Large bodies go in a pending key; the pub/sub message is only a trigger.

## Auth and env gotchas

- Each app has its own `.env`. Never print or commit secrets.
- `Authorization` carries the **raw key, no `Bearer`**.
- data-api, notifier and storage refuse to start without `<APP>_AUTH_KEY ?? AUTH_KEY`. bot, dashboard and data-api share the key; without it the dashboard skips every call and channel/role/player features look like 502s.
- `AUTH_KEY` rotation also affects notifier's stored webhook tokens: read `apps/notifier/AGENTS.md` first.
- `LAVALINK_HOSTS`: comma-separated `id_host_port[_password]`.
- Package-specific env (data-api LLM, storage URLs, shardmanager key) lives in that package's `AGENTS.md`.
